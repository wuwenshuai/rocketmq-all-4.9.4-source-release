## 1. 丢消息：按链路拆

### 生产端

| 原因 | 你怎么验证 | 怎么防 |
|------|------------|--------|
| ONEWAY 发送 | 代码里是 oneway | 重要消息别用 |
| 异步发送失败没处理 | 看回调是否吃掉异常 | 回调里重试/落库 |
| 同步发送失败直接忽略 | 看业务是否检查 SendResult | 失败告警+补偿 |
| 超时当作失败又重发 | 可能造成重复而不是丢 | 幂等 |

### Broker 端

| 原因 | 说明 |
|------|------|
| 异步刷盘 + 掉电 | PageCache 未落盘 |
| 异步复制 + Master 宕机切换 | Slave 少数据 |
| 磁盘满 / 写失败 | 看 `store.log` |
| 延时/事务状态处理不当 | 半消息回滚或永不承诺 |

### 消费端

| 原因 | 说明 |
|------|------|
| 业务异常但返回成功 | 「逻辑丢失」 |
| 位点被错误重置到最新 | 中间消息跳过 |
| 订阅错 Topic/Tag | 根本没收到 |

### 本地演练建议

1. 用 ONEWAY 发 100 条，Consumer 计数 —— 体会「可能少」
2. 正常 SYNC 发 100 条，Consumer 计数 —— 对比
3. 看 `~/logs/rocketmqlogs/broker.log` / `store.log` 有无 ERROR

## 2. 重复消费：为什么几乎不可避免

RocketMQ 倾向 **至少一次**。重复来源：

1. 生产重试（Broker 超时，生产端重发，实际第一次已成功）
2. 消费成功后，提交位点前进程挂了
3. 消费失败返回重试
4. 网络重传导致 Broker 认为需要再投

### 正解

业务幂等：唯一键去重（DB 唯一索引 / Redis setnx / 状态机）。

### 本地演练

在 Consumer 里打印 `msg.getMsgId()`，然后：

1. 正常消费
2. 故意在处理成功后 `System.exit(1)` 再重启 Consumer  
   看是否会重新消费同一条（可能发生）

## 3. 削峰：MQ 不是自动挡

面试题：「用了 RocketMQ 一定能削峰吗？」

答案：**不一定。**

削峰成立的前提：

```text
入口洪峰 ──▶ MQ 堆积缓冲 ──▶ 下游按自己能力慢慢消费
```

如果：

- 消费者线程无限扩，把下游 DB 打爆
- 队列很短 / 磁盘满开始阻塞生产
- 下游和上游一样强依赖同步链路

那就削不了峰。

### 正确用法

1. 限制消费并发
2. 预估堆积容量（磁盘、保存时间）
3. 下游有限流、降级
4. 监控堆积量并告警

### 本地小实验

1. Producer 快速发 5000 条
2. Consumer `sleep(50ms)` 限速
3. `consumerProgress` 看堆积先升后降  
   这就是削峰的直观样子

## 4. 消息队列常见坑（面试可直接背）

1. **忘了幂等**：重复消费导致重复下单
2. **队列数不合理**：消费者加了实例也不加速
3. **大消息**：几 MB 的消息拖垮性能（应放 OSS + 传链接）
4. **堆积不监控**：爆盘才发现
5. **顺序消息滥用**：全局有序拖垮吞吐
6. **Tag 过滤误解**：SQL 过滤要开启能力，不是随便能用
7. **本地事务 + 普通消息**：没用事务消息导致不一致
8. **消费阻塞**：业务同步调下游，把消费线程占满
9. **时间回拨 / 超时设置过短**：误判失败
10. **多环境 namesrv 配错**：连到别的集群
