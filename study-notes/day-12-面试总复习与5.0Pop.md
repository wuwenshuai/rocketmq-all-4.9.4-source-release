## 1. 17 题速答骨架（先写自己的话，再对照）

建议你合上文档，按题号各说 60～90 秒。下面是标准骨架：

1. **事务消息**：半消息 → 本地事务 → commit/rollback → 回查  
2. **顺序**：分区顺序 = 同键同队列 + 顺序消费加锁  
3. **不丢失**：同步发送 + 同步刷盘/复制 + 消费确认 + 监控  
4. **延时**：4.x 固定 level + 调度 Topic + 到期投递  
5. **集群**：单 Master / 多 Master / 多主多从异步 / 同步（+DLedger）  
6. **堆积**：看 progress，扩容/提速/治热点/加队列  
7. **工作流程**：注册路由 → 发 → 存 → 拉 → 提交位点  
8. **分发**：客户端选队列；消费侧按队列分配  
9. **推拉**：API Push，实现 Pull + 长轮询  
10. **削峰**：能，但要限速消费并预留堆积能力  
11. **Pop**：见下一节  
12. **vs Kafka 事务**：业务回查 vs 多分区原子写  
13. **重平衡**：有，但分的是队列；注意队列数  
14. **丢消息原因**：oneway/异步刷盘/位点重置/逻辑丢  
15. **重复原因**：至少一次 + 超时重试；靠幂等  
16. **普通 vs 顺序**：吞吐 vs 同键有序；状态机场景用顺序  
17. **坑**：幂等、队列数、大消息、监控、滥用顺序

## 2. RocketMQ 5.0 Pop 模式（概念）

你手里是 **4.9.4**，没有完整 5.0 Pop 服务端实现可跟。面试这样说就够：

### 为什么要有 Pop？

传统 Pull/Push：

- 消费进度由客户端管理感很强
- 锁队列、重平衡复杂
- 对无状态、网关型消费不够友好

Pop 消费：

- 更像「从 Broker 弹出一条（批）消息」
- **位点/不可见时间（invisible time）更多由 Broker 侧管理**
- 消费成功 ACK；失败到点重新可见，可再被领取
- 适合 Kubernetes、无状态扩缩容、多语言客户端

对比：

| | 经典 Push/Pull（4.x 主模型） | Pop（5.x） |
|--|------------------------------|------------|
| 进度 | 客户端+Broker offset 协作 | Broker 侧认领/ACK 更重 |
| 重平衡 | 队列分配 | 更易无状态扩缩 |
| 场景 | Java 重客户端生态 | 云原生、多语言 |

一句话：

> Pop 把「谁拿走了消息、多久没确认就还回去」变得更像队列的 claim/ack 模型。
